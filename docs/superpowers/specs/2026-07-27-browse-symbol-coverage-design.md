# ブラウズ画面 銘柄カバレッジ表（SP2）設計

**日付:** 2026-07-27
**位置づけ:** ブラウズ画面刷新 3 部作の第 2 部。SP1（レシピ・ロールアップ、PR #333）の続き
**範囲:** フロントエンドのみ。バックエンド（Python）・`alpha-forge` には一切変更を入れない

---

## 1. 解く問題

SP1 で表の単位を `strategy_id` からレシピ `(name, 実効銘柄, timeframe)` に変えた。その結果、
ブラウズ画面には**単位の食い違い**と**答えられない問い**の 2 つが残っている。

### 1.1 単位の食い違い（実データで確認済み）

現在の銘柄アトラスは戦略単位で数えている。同じ画面の表はレシピ単位で数えている。

| 銘柄 | アトラスの表示（戦略数） | 表の単位（レシピ数） |
|---|---|---|
| SPY | 87 件 | 51 レシピ |
| QQQ | 62 件 | 27 レシピ |
| NVDA | 55 件 | 25 レシピ |

同じ画面で同じ銘柄が違う数で出る。SP1 が単位を変えた副作用であり、放置すると
どちらが正しいのか読み手が判断できない。

### 1.2 「次に何を回すか」に答えられない

アトラスのカードは `最高 Sharpe` / `平均 Return` / `最終実行` の 3 指標を出す。
これは**すでに回した結果**しか語らない。実データには未実行レシピが 139 件ある
（全 275 レシピの 51%）が、それがどの銘柄に溜まっているのかは画面のどこにも出ない。

実測（実データ 475 戦略 / 275 レシピ / 実効銘柄 46 + 未割当 = 47 行）:

- 一度もバックテストしていない銘柄が 11 件（ADBE / AMZN / AUDUSD=X / AVGO / GOOGL /
  IEF / META / MSFT / NFLX / SCHD / VYM）
- 実行済みが偏っている銘柄の例: IWM は 11 レシピ中 2 件のみ実行済み

現状の画面ではこの 11 件は「最高 Sharpe が `—`」のカードとして他 36 件に紛れ、
IWM の偏りに至っては表示されている情報からは読み取れない。

未実行が溜まっている上位（実測）:

| 銘柄 | レシピ | 実行済 | 未実行 |
|---|---:|---:|---:|
| SPY | 51 | 22 | 29 |
| NVDA | 25 | 9 | 16 |
| QQQ | 27 | 12 | 15 |
| GC=F | 18 | 6 | 12 |
| IWM | 11 | 2 | 9 |
| BTC-USD | 16 | 8 | 8 |

### 1.3 副次的な問題（今回のスコープには含めない）

アトラスは折り畳み時 40px、展開時 1,999px を占める。SP1 で既定を折り畳みにしたため
通常の閲覧の邪魔にはなっていない。**本 SP2 は高さ削減を目的としない**（後述 §7）。

## 2. 採らなかった案

### 案 A: 銘柄 × 指標のマトリクス（当初の SP1 PR に「SP2 の予定」として書いたもの）

「どの銘柄でどの指標を試したか」を格子で見せる案。**実データで密度を測って棄却した。**

- 47 銘柄 × 181 タグ組み合わせ = 8,507 セル
- うち埋まるのは 209 セル = **2.5%**
- さらに 475 戦略のうち 19 件はタグを 1 つも持たず、格子のどこにも置けない

97.5% が空白の格子は、走査コストだけ高くて情報がない。マトリクスは軸の
カーディナリティが小さいときにだけ機能するが、タグ組み合わせは戦略ごとにほぼ
一意（181 組み合わせ / 475 戦略）で、軸として成立していない。

### 案 B: 新しいモード（タブ）としてカバレッジ画面を作る

SP1 で 3 モードタブのシェルを「切り替え先が 1 つしかないタブバーは投機的」として
見送った。SP2 でもその判断を維持する。カバレッジは**独立したビューではなく、
表を絞り込むためのナビゲーション**であり、既存の折り畳みの中身を差し替えれば足りる。

タブシェルの導入判断は SP3（整理モード）で 3 つ目のビューが確定した時点で行う。

## 3. 採る案: 銘柄カバレッジ表

既存の折り畳みセクションの中身を、カードグリッドからソート可能な表に差し替える。

### 3.1 列

| 列 | 内容 | 現アトラスとの差分 |
|---|---|---|
| 銘柄 | `SPY` / `USDJPY=X` / `未割当` | 同じ（クリックで絞り込みも同じ） |
| 区分 | 指数 / ETF / 個別銘柄 / FX / コモディティ / その他 | セクション見出し → 列へ |
| レシピ | その銘柄のレシピ数 | **戦略数 → レシピ数**（§1.1 の修正） |
| 実行済 | `runCount > 0` のレシピ数 | 新規 |
| 未実行 | `runCount === 0` のレシピ数 | **新規（本 SP2 の主目的）** |
| 最高 Sharpe | best variant の最大値 | 集計母数がレシピの best に変わる |
| 平均 Return | best variant の平均値 | 集計母数がレシピの best に変わる |
| 最終実行 | 最も新しい実行日時 | 同じ |

区分を列にすることで、資産クラスごとのセクション分割（現在 6 セクション、
各セクションが見出し + カードグリッド）が消え、1 つの表に統合される。
区分での絞り込みが必要になったら列ヘッダのソートで代替できる。

### 3.2 既定ソート

**未実行の多い順。** 「次に何を回すか」に直接答える並びにする。

同数のときの決定順序（テストで固定する）:

1. 未実行レシピ数 降順
2. レシピ数 降順
3. 最高 Sharpe 降順（`null` は最後）
4. 銘柄名 昇順

列ヘッダのクリックで他の軸にも並べ替えられる。本体の表と同じ操作感に揃える:

- 別の列を初めてクリックしたときは**降順**から始める
- 同じ列を再クリックすると昇順・降順が反転する
- 主キーはクリックされた列。並びが決まらないときは上記 1〜4 のうち**主キーと重複しない
  ものを記載順に**適用する（例: レシピ数で並べたときのタイブレークは 1 → 3 → 4）

`未割当` 行は**どの並べ替えでも常に末尾に固定する**（現行 `compareSymbolStats` の
挙動を踏襲）。銘柄そのものが不明な行は「次に回す候補」にも「成績の比較対象」にも
ならないため、並べ替えの対象から外して末尾に置く。

### 3.3 ソート状態の持ち方

**コンポーネントローカルの `useState`。URL クエリには載せない。**

本体の表は `?sort=` / `?dir=` を URL に持つが、カバレッジ表のソートは URL に載せない。
理由は 2 つ:

1. `SavedViews` が URL パラメータを保存する仕組みのため、載せると保存ビューに
   カバレッジ表の並び順まで混入する
2. 既定で折り畳まれているセクションの並び順は共有・復元する価値が薄い

`CollapsibleSection` が既に自前で `useState` を持っている前例に倣う
（`components/` 配下のコンポーネントは状態を持ってよい。`screens/` は持てない）。

### 3.4 行の操作

- 行クリックでその銘柄を絞り込みトグル（既存 `toggleSymbol` の挙動を維持）
- 選択中の行はハイライトし、他の銘柄が選択されているときは減光する（現行カードと同じ）
- `未割当` 行は絞り込めない（現行カードと同じく無効化）

**絞り込み状態の読み書きは `useSearchParams` でコンポーネント内から行う**
（現行 `SymbolAtlas` と同じ方式）。`BrowseScreen` へコールバックを増やさない。

アクセシビリティは本体の表と同じ方式を採る。`<tr>` に `onClick` を置くだけでは
キーボード操作できないため、銘柄セルの中に実 `<button aria-pressed>` を置き、
そこがフォーカス可能な操作点になる。列ヘッダは既存の `SortHeaderCell`
（`<th scope="col" aria-sort>` + 実 `<button>`）を再利用する。

`<tr>` の `onClick` とボタンの `onClick` が二重に発火してトグルが打ち消し合わないよう、
ボタン側で `stopPropagation` する（本体の `StrategyRow` がチェックボックスのセルで
使っているのと同じ手当て）。

### 3.5 レスポンシブ

8 列は 768px 以下では収まらない。本体の表と同じく `u-col-hide-md-down` を使って
狭い画面では列を落とす。

| 幅 | 表示する列 |
|---|---|
| 769px 以上 | 全 8 列 |
| 768px 以下 | 銘柄 / レシピ / 実行済 / 未実行 / 最高 Sharpe |

区分・平均 Return・最終実行を落とす。**未実行は本 SP2 の主目的なのでどの幅でも落とさない。**

### 3.6 見出しと名前

セクション名を「銘柄アトラス」から「**銘柄カバレッジ**」（英: `Symbol coverage`）に変える。
中身がカードの一覧（アトラス）から網羅状況の表（カバレッジ）に変わるため、
名前が実態と合わなくなる。

折り畳みラベルの件数表記も、レシピ単位に揃える:

```
現在: 銘柄アトラス（46 銘柄）
変更: 銘柄カバレッジ（47 銘柄 · 未実行 139 レシピ）
```

> **注:** 現行ラベルの「46 銘柄」は `list.symbols.length`（`未割当` を含まない実効銘柄の
> ユニーク数）。表の行数は `未割当` 行を含むため 47 行になり、ラベルと 1 ずれる。
> **ラベルの銘柄数は表の行数（`stats.length`）と一致させる**ことでこのずれを解消する。

## 4. データの流れ

### 4.1 集計単位を `StrategyListItem[]` から `Recipe[]` へ

```
useStrategyList
  ├─ all: StrategyListItem[]        （API から。フィルタ前）
  ├─ allRecipes: Recipe[]           ★新規に公開。buildRecipes(all)
  │                                  （現在は recipeTotal のために内部で計算済み）
  └─ recipes: Recipe[]              （フィルタ・未実行除外・ソート後。本体の表用）

BrowseScreen
  └─ SymbolCoverageTable recipes={list.allRecipes} lang={lang}
       └─ useSymbolStats(recipes) → SymbolStat[]
```

カバレッジ表は**フィルタ前の全レシピ**を集計する。現行アトラスが `list.all`
（フィルタ前の全戦略）を受け取っているのと同じ方針。絞り込むためのナビゲーションが
絞り込み結果に応じて変動すると、絞り込みを解除する手がかりが消える。

`recipeTotal` は `allRecipes.length` から導出する（現在の `buildRecipes(all).length` と同値）。

`recipes` が空のときは表を描画せず `null` を返す（現行 `SymbolAtlas` が
`sections.length === 0` で `null` を返すのと同じ）。`BrowseScreen` 側でも
`list.all.length > 0` を条件に折り畳みごと出さないガードが既にある。

### 4.2 `SymbolStat` の変更

```ts
export interface SymbolStat {
  symbol: string | null        // null = 未割当
  assetClass: AssetClass
  recipeCount: number          // 旧 count（戦略数 → レシピ数）
  runRecipeCount: number       // 新規
  unrunRecipeCount: number     // 新規
  bestSharpe: number | null
  avgReturnPct: number | null
  lastRunAt: string | null
}
```

**不変条件（テストで固定する）:**

1. `recipeCount === runRecipeCount + unrunRecipeCount`（全レシピ行について）
2. `Σ recipeCount === recipeTotal`（レシピは実効銘柄をちょうど 1 つ持つため、
   全銘柄の合計は表フッタの全レシピ数と一致する）
3. `unrunRecipeCount === recipeCount` ⟺ その銘柄は一度も実行されていない
   ⟺ `bestSharpe === null` かつ `lastRunAt === null`

指標 3 種（`bestSharpe` / `avgReturnPct` / `lastRunAt`）は `recipe.best` から取る。
`best === null`（＝未実行レシピ）は集計から除外する。SP1 で確立した
「レシピの指標は best 1 件から取る」原則をそのまま銘柄集計にも適用する
（列ごとに最大を取ると実在しない戦略の成績を合成表示することになる）。

## 6. テスト

現在 `SymbolAtlas` / `SymbolCard` / `useSymbolStats` には**単体テストが 1 つも無い**。
SP2 で新規に用意する。

### 6.1 `useSymbolStats`

- レシピを銘柄ごとに振り分ける（`effectiveSymbol` 経由。`item.symbol` が空でも
  `target_symbols[0]` から解決される）
- `recipeCount === runRecipeCount + unrunRecipeCount` を、実行済と未実行が混在する
  銘柄で検証する
- 全レシピの合計が入力レシピ数と一致する（§4.2 不変条件 2）
- 未実行のみの銘柄で `bestSharpe === null` / `lastRunAt === null` / `avgReturnPct === null`
- 指標が `recipe.best` から取られている（同じレシピ内で best より高い Sharpe を持つ
  variant を用意し、それが拾われないことを確認する）
- 既定ソートの決定順序を、4 段のタイブレークすべてが効く入力で固定する
- `未割当` が末尾に来る

### 6.2 `SymbolCoverageTable`

- 未実行の多い銘柄が先頭に出る
- 一度も実行していない銘柄の行で、実行済が `0`・未実行がレシピ数と等しい
- 列ヘッダのクリックでソート軸が変わり、同じ列の再クリックで方向が反転する
- 銘柄セルのボタンをクリックすると URL の `?symbol=` にその銘柄が入り、
  もう一度クリックすると外れる（`MemoryRouter` で包み、遷移後の検索文字列を検証する）
- 行の `<tr>` をクリックしても同じく 1 回だけトグルする（二重発火しない）
- `未割当` 行のボタンは無効
- 768px 以下で落とす列に `u-col-hide-md-down` が付いており、未実行の列には付いていない

### 6.3 判別力の確認（ablation）

実装をわざと退行させてテストが落ちることを確認する。SP1 で「`variants` は
Sharpe 降順のため `best === variants[0]` となり、想定した退行が判別不能だった」
という取りこぼしがあったため、各 ablation が本当に落ちることを実行して確かめる。

- 未実行カウントを `runCount === 0` ではなく `variantCount === 0` で数える
  → 全銘柄の未実行が 0 になり、既定ソートと不変条件のテストが落ちること
- 指標を `best` ではなく `variants[0]` から取る
  → §6.1 の「best から取られている」テストが落ちること
- 既定ソートを未実行降順ではなくレシピ数降順に戻す
  → 順序固定のテストが落ちること

### 6.4 E2E

既存の `browse.spec.ts` の折り畳みテスト（既定で畳まれている → 展開すると見出しが出る）を
新しい見出し名で通す。表の内容に踏み込んだ E2E は追加しない（単体テストで足りる）。

### 6.5 ゲート

`tsc --noEmit` は `tsconfig` の `files: []` により 0 ファイルを検査するため常に成功する。
型検査の実ゲートは `pnpm run build`（`tsc -b && vite build`）。

- `pnpm vitest run`
- `pnpm run lint`（パイプに繋がず単独行で実行し、終了コードを確認する）
- `pnpm run build`
- `pnpm run e2e`
- `pnpm run screenshots`（見た目が変わるため再撮影が必要）
- `uv run pytest tests/ -q` / `uv run ruff check src/ tests/`（バックエンド無変更の回帰確認）

## 7. 明示的に目的としないこと

**ページ高の削減。** 表は 47 行 × 約 36px ≒ 1,700px で、現行のカードグリッド 1,999px と
大きくは変わらない。既定で折り畳まれているため通常時はどちらも 40px。
本 SP2 の狙いは**走査性と未実行の可視化**であり、高さではない。

**行の仮想化。** 47 行では不要。

**指標タグによる分析。** 案 A で棄却したマトリクスの残骸を持ち込まない。

**削除・整理機能。** SP3 の範囲。

## 8. 未解決事項

**行高の環境差（issue #334）。** 実データで表の行高が 55px、E2E フィクスチャで 44px に
なる原因は SP1 時点で未特定のまま。カバレッジ表の行高（§7 で 36px と見積もった）も
同じ影響を受ける可能性がある。SP2 ではこの問題を追わず、見積もりが外れた場合は
実測値をそのまま報告する。
